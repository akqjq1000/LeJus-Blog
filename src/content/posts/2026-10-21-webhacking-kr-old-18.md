[webhacking.kr](https://webhacking.kr)의 **old-18** 문제를 풀었다.
가장 고전적인 **SQL 인젝션** 입문 문제로, 사용자 입력이 `WHERE` 절에
**아무런 처리 없이 그대로** 들어갈 때 어떤 일이 벌어지는지,
그리고 **빈약한 필터링(공백 차단)** 이 왜 방어가 되지 못하는지를 보여준다.

"페이로드 하나 넣으면 끝"에서 멈추지 않고, **쿼리가 실제로 어떻게 조립되는지**
와 **연산자 우선순위** 까지 따라가며 왜 그 입력이 통하는지 정리한다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-18 |
| 유형 | SQL Injection (공백 필터 우회) |
| 목표 | `guest`가 아닌 **`admin` 계정**을 조회해 통과 |

문제 페이지에는 번호를 입력받는 검색 폼이 하나 있고,
입력한 번호(`no`)로 회원을 조회해 그 결과가 `admin`이면 문제가 풀린다.

## 2. 소스 코드

문제에서 공개하는 핵심 로직은 대략 다음과 같다.

```php
<?php
  $db = dbconnect();
  if(preg_match('/ |\/|\(|\)|\t|%09|%0a|%0b|%0c|%0d/i', $_GET['no'])) exit("no hack");
  $result = mysqli_query($db, "select id from member where id='guest' and no=$_GET[no]");
  $data = mysqli_fetch_array($result);
  if($data['id'] == "guest") echo "hi guest";
  if($data['id'] == "admin"){
    solve(18);
    echo "hi admin!";
  }
?>
```

여기서 눈여겨볼 지점은 두 가지다.

1. `$_GET[no]`가 **따옴표도 없이** 쿼리에 그대로 삽입된다 → **숫자 컨텍스트 인젝션**.
2. 필터는 **일부 공백류·괄호만** 막는다 — 실제 문자로는 `공백`, `탭(\t)`, `/`, `(`, `)`,
   그리고 **문자열 `%09`~`%0d`** 를 차단한다.
   즉 **키워드 자체(`or`, `and` …)는 막지 못하고**, 뒤에서 볼 **인코딩·디코딩의 틈**도 남아 있다.

데이터베이스에는 `guest`(no=1)와 `admin`(no=2)이 있다고 가정한다.

## 3. 쿼리가 어떻게 조립되는가

정상 입력 `no=1`이면 쿼리는 이렇게 된다.

```sql
select id from member where id='guest' and no=1
```

`id='guest'` **그리고** `no=1` 이 모두 참이라 guest 행이 나온다. 여기서 중요한 건
**`admin` 행을 반환시키는 것** 인데, `id='guest'`가 앞에 고정돼 있어 그대로는 admin이 걸리지 않는다.

`OR`를 끼워 넣어 조건을 하나 더 만든다. 단순히 `no=2`만 주면
`id='guest' and no=2` → guest의 no는 1이므로 **거짓**, 아무것도 안 나온다.
그래서 **`or`로 admin 행을 직접 겨냥** 해야 한다.

핵심은 **연산자 우선순위**다. SQL에서 `AND`가 `OR`보다 먼저 묶이므로,
목표는 아래와 같이 해석되는 쿼리를 만드는 것이다.

```sql
select id from member where (id='guest' and no=0) or (no=2)
```

앞 괄호는 거짓이지만 뒤의 `no=2`가 admin 행과 일치하므로 **admin이 반환**된다.
문제는 `no=0 or no=2`를 그대로 넣으면 `or` 양옆 **공백에서 `no hack`으로 걸린다**는 것이다.

## 4. 공백 필터 우회 — 인코딩과 디코딩의 틈

필터를 다시 보면, 막는 대상은 **실제 공백·탭**과 **문자열 `%09`~`%0d`** 다.

```php
if(preg_match('/ |\/|\(|\)|\t|%09|%0a|%0b|%0c|%0d/i', $_GET['no'])) exit("no hack");
```

여기서 결정적인 틈은 **PHP가 `$_GET['no']`를 이미 URL 디코딩한 뒤** 필터에 넘긴다는 점이다.
URL에 `%0a`를 넣어 보내면, 필터가 보는 값은 **문자열 `"%0a"`가 아니라 디코딩된 개행 문자(0x0a)** 다.

- 필터의 `%0a`~`%0d` 패턴은 **문자열** `"%0a"`를 막는 것이라, 디코딩된 **개행 문자**에는 걸리지 않는다
  (이 패턴은 `%250a`처럼 **이중 인코딩**을 넣었을 때나 매칭된다).
- 실제 문자로 막는 건 **공백과 탭(`\t`)뿐** — **개행(0x0a)·캐리지리턴(0x0d) 등은 실제 문자로는 막지 않는다.**
- 그리고 SQL은 **개행도 공백처럼** 토큰 구분자로 취급한다.

그래서 공백 대신 **URL 인코딩된 개행** 을 키워드 사이에 끼우면 그대로 통과한다.

```
?no=0%0aor%0ano=2
```

디코딩 후 실제로 조립되는 쿼리(⏎ = 개행):

```sql
select id from member where id='guest' and no=0⏎or⏎no=2
```

우선순위에 따라 `(id='guest' and no=0) or (no=2)` 로 해석되고,
뒤 절이 admin 행과 일치해 **`admin`이 조회**된다.
개행 외에 `%0b`(수직 탭)·`%0c`(폼 피드)·`%0d`(캐리지리턴)처럼 **필터가 실제 문자로는 막지 않는 공백류** 도 같은 방식으로 쓸 수 있다.

> 참고: 공백 우회에는 인라인 주석 `/**/`나 논리 연산자 `||`도 흔히 거론되지만,
> 이 문제는 `/`를 막아 주석을 쓸 수 없고, `||` 역시 이 환경에서는 통하지 않는다.
> 필터가 **실제 문자로는 놓치는 공백류** 를 쓰는 것이 이 문제의 정답에 가깝다.

```console
GET /challenge/web-32/index.php?no=0%0aor%0ano=2
→ hi admin!
```

> 이 문제는 **따로 제출할 플래그 문자열이 없다.** `admin` 행이 조회되는 순간
> 서버가 `solve(18)`을 호출해 **그 입력 자체로 바로 통과** 처리된다.
> 즉 "비밀 값을 알아내는" 문제가 아니라 **의도된 입력(통과 조건)을 만들어 넣는** 문제다.

## 5. 왜 취약한가 — 그리고 올바른 방어

이 문제의 본질은 **필터가 아니라 쿼리 조립 방식**에 있다.
블랙리스트(공백·괄호 차단)는 언제나 우회가 나온다 — 특히 **인코딩된 공백**처럼
필터가 보는 값과 실제 실행되는 값이 어긋나는 지점이 생긴다.

제대로 된 방어는 **입력을 쿼리 문자열에 섞지 않는 것** 이다 — **파라미터 바인딩(prepared statement)**.

```php
$stmt = $db->prepare("select id from member where id='guest' and no=?");
$stmt->bind_param("i", $_GET['no']);   // 정수로 바인딩
$stmt->execute();
```

이렇게 하면 `no`는 **데이터로만** 취급되어 `0%0aor%0ano=2` 같은 입력이 쿼리 구조를 바꾸지 못한다.
추가로 `no`는 숫자여야 하므로 `ctype_digit()`으로 **타입 검증**까지 두면 더 좋다.

## 6. 정리

- 따옴표 없는 **숫자 컨텍스트**라도 인젝션은 성립한다 — 입력이 쿼리에 직접 들어가면 끝.
- `AND`가 `OR`보다 먼저 묶인다는 **연산자 우선순위**가 `0 or no=2` 페이로드의 핵심이다.
- **블랙리스트 필터는 방어가 아니다** — 특히 **PHP가 먼저 URL 디코딩**하므로, 필터가 막는 문자열(`%0a`)과
  실제 실행되는 문자(개행)가 어긋나 공백 차단이 무력화된다.
- 올바른 해법은 **prepared statement + 타입 검증**. 입력을 구조가 아닌 데이터로 다뤄야 한다.

> 필터를 한 겹 더 쌓는 대신, "사용자 입력이 쿼리의 **구조**를 바꿀 수 있는가"를 먼저 묻는다.
