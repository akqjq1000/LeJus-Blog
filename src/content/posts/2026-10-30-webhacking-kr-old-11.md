[webhacking.kr](https://webhacking.kr)의 **old-11** 문제를 풀었다.
SQL 인젝션도 쿠키 위조도 아니고, **정규식(regex) 하나를 읽어내는** 문제다.
핵심은 세 가지다. **서버가 접속자의 IP를 정규식 패턴 안에 그대로 보간**한다는 점,
패턴 안의 `\t`가 **문자 `\`+`t`가 아니라 탭 문자**라는 점(PHP 큰따옴표 함정),
그리고 `preg_match`에 **앵커(`^`·`$`)가 없어** 입력 어디에서든 매칭된다는 점이다.

"패턴 보고 대충 맞춰 넣기"에서 멈추지 않고, **PHP가 그 패턴 문자열을 실제로 어떻게 해석하는지**
와 **왜 탭이 아니면 틀리는지**를 실패 케이스까지 서버에 직접 넣어가며 정리한다.
아래 내용은 전부 **실제로 서버에 넣어 통과(그리고 실패)를 확인한 것**이다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-11 (`/challenge/code-2/`) |
| 유형 | 정규식 분석 / 동적 패턴·이스케이프 해석 |
| 배점 | 30점 |
| 목표 | `val` 파라미터를 서버가 만든 **정규식에 매칭**시켜 통과 |

처음 페이지에 들어가면 **`Wrong`** 만 뜨고, 하단에 `view-source` 링크가 있다.
입력창도 버튼도 없다. 즉 **GET 파라미터 `val`을 직접 넘겨야** 하는 문제다.

## 2. 정보 수집 — 소스 코드

하단 `view-source`(`?view_source=1`)로 전체 로직이 공개된다. 핵심은 딱 이 세 줄이다.

```php
<?php
  $pat="/[1-3][a-f]{5}_.*$_SERVER[REMOTE_ADDR].*\tp\ta\ts\ts/";
  if(preg_match($pat,$_GET['val'])){
    solve(11);
  }
  else echo("<h2>Wrong</h2>");
?>
```

`$_GET['val']`이 `$pat`에 매칭되면 `solve(11)`이 호출된다. 그래서 **이 패턴 문자열이
PHP 눈에 실제로 어떻게 보이는지**를 정확히 해석하는 게 전부다. 두 가지가 숨어 있다.

### 2-1. `$_SERVER[REMOTE_ADDR]` — 내 IP가 패턴에 박힌다

패턴이 **큰따옴표(`"`)** 문자열이라는 점이 핵심이다. PHP는 큰따옴표 문자열 안에서
변수를 **보간(interpolation)** 한다. `$_SERVER[REMOTE_ADDR]`처럼 **따옴표 없는 키**도
큰따옴표 문자열 안에서는 그대로 배열 참조로 풀린다. 즉 패턴에는 내 IP가 들어간다.

이번 세션에서 서버가 본 내 IP는 `14.41.76.65`였다(같은 사이트의 `bonus-4` 페이지가
`client ip`로 `REMOTE_ADDR`을 그대로 찍어줘서 확인했다). 그러면 패턴의 그 자리는
`14.41.76.65`가 된다. **접속자마다 패턴이 달라진다**는 뜻이다.

### 2-2. `\tp\ta\ts\ts` — `\t`는 탭 문자다

여기가 이 문제의 진짜 함정이다. 패턴은 큰따옴표 문자열이므로 `\t`는 **이스케이프 시퀀스**로
해석돼 **탭 문자(0x09)** 가 된다. 그래서 `\tp\ta\ts\ts`는 정규식에 다음과 같이 들어간다.

```
<TAB>p<TAB>a<TAB>s<TAB>s
```

세로로 읽으면 `p a s s` = "pass"지만, 글자 사이사이가 **공백이 아니라 탭**이다.
"pass"라고 그냥 쓰거나 공백으로 끼워 넣으면 **틀린다**(§4에서 둘 다 넣어 확인한다).

### 2-3. 앵커가 없고 `.`은 아무 글자나 매칭한다

`preg_match`는 `^`·`$` 앵커가 없으면 **문자열 어디에서든** 부분 매칭을 찾는다.
또 패턴 안의 `.`(IP의 점 포함)은 **임의의 한 글자**를 뜻한다. IP를 넣을 때
점을 그대로 `.`로 적으면 당연히 매칭되고, 심지어 아무 글자여도 매칭된다.
`.*` 두 개는 각각 **비어 있어도** 되고 아무 문자열이나 끼어도 된다.

정리하면, PHP가 보는 최종 패턴(내 IP 기준)은 다음과 같다.

```
/[1-3][a-f]{5}_.*14.41.76.65.*<TAB>p<TAB>a<TAB>s<TAB>s/
```

## 3. 문제점 — 어디가 "읽기 어렵게" 설계됐나

이 문제의 난이도는 취약점이라기보다 **"소스를 눈대중으로 읽으면 반드시 틀리게"**
만든 두 함정에 있다.

1. **동적으로 조립되는 패턴.** 패턴에 `$_SERVER[REMOTE_ADDR]`을 보간해
   **접속자마다 정답이 달라진다.** 남의 풀이를 그대로 복붙하면 IP가 안 맞아 실패한다.
2. **이스케이프 해석의 혼동.** 큰따옴표 안의 `\t`는 "백슬래시+t"가 아니라 탭이다.
   소스를 겉으로만 보면 "pass"를 넣으면 될 것 같지만, 실제로는 **탭 문자 4개**가 필요하다.

둘 다 "코드가 문자열을 어떻게 해석하는가"를 **한 단계 더** 따라가야 보인다.

## 4. 익스플로잇 — 페이로드 설계와 단계별 검증

필요한 `val`을 패턴 조각 순서대로 맞춰 조립한다.

| 패턴 조각 | 의미 | 넣을 입력 |
| --- | --- | --- |
| `[1-3]` | 1~3 중 한 자리 | `1` |
| `[a-f]{5}` | a~f 다섯 글자 | `abcde` |
| `_` | 밑줄 | `_` |
| `.*` | 아무거나(생략 가능) | (빈 값) |
| `14.41.76.65` | 내 IP | `14.41.76.65` |
| `.*` | 아무거나(생략 가능) | (빈 값) |
| `\tp\ta\ts\ts` | 탭+p 탭+a 탭+s 탭+s | `<TAB>p<TAB>a<TAB>s<TAB>s` |

이어 붙이면 최종 입력은 다음과 같다(가운데 사이사이는 **탭 문자**).

```
1abcde_14.41.76.65<TAB>p<TAB>a<TAB>s<TAB>s
```

URL에서는 탭을 `%09`로 인코딩하므로 요청은 이렇게 된다.

```
GET /challenge/code-2/?val=1abcde_14.41.76.65%09p%09a%09s%09s
```

### 4-1. 패턴 해석을 먼저 로컬에서 검증

서버에 넣기 전에, PHP가 보는 것과 **같은 패턴**을 자바스크립트로 그대로 만들어
위 입력이 매칭되는지 확인했다(`\t`는 실제 탭, IP는 보간된 값).

```js
const ip = '14.41.76.65', T = '\t';
// PHP 큰따옴표 패턴과 동일: \t = 탭, $_SERVER[REMOTE_ADDR] = ip
const re  = new RegExp('[1-3][a-f]{5}_.*' + ip + '.*' + T+'p'+T+'a'+T+'s'+T+'s');
const val = '1abcde_' + ip + T+'p'+T+'a'+T+'s'+T+'s';
re.test(val);   // → true
```

### 4-2. 서버에 실제 전송 → 통과

같은 `val`을 실제 문제 URL로 보냈다.

```js
const url = 'https://webhacking.kr/challenge/code-2/?val='
          + encodeURIComponent('1abcde_14.41.76.65\tp\ta\ts\ts');
await fetch(url, { credentials: 'include' }).then(r => r.text());
```

```console
GET /challenge/code-2/?val=1abcde_14.41.76.65%09p%09a%09s%09s
→ alert('old-11 Pwned!');
→ old-11 Pwned. You got 30point. Congratz!
```

### 4-3. 실패 케이스로 "왜 그래야 하는지" 못 박기

주장(탭이어야 한다, IP가 맞아야 한다, 접두가 필요하다)을 그냥 믿지 않고
**틀린 입력도 전부 서버에 넣어** `Wrong`이 뜨는지 확인했다.

| 넣은 `val` | 서버 응답 | 확인되는 사실 |
| --- | --- | --- |
| `1abcde_<IP><TAB>p<TAB>a<TAB>s<TAB>s` | 통과 | 정답 |
| `1abcde_<IP>pass` (탭 없이) | `Wrong` | `\t`는 문자가 아니라 **탭** |
| `1abcde_<IP> p a s s` (공백) | `Wrong` | 공백이 아니라 **탭이어야** 함 |
| `1abcde_1.2.3.4<TAB>...` (IP 틀림) | `Wrong` | 패턴에 **내 IP가 박혀** 있음 |
| `<IP><TAB>p<TAB>a<TAB>s<TAB>s` (접두 없음) | `Wrong` | `[1-3][a-f]{5}_` 필요 |
| `1abcd_<IP><TAB>...` (a~f 4글자) | `Wrong` | `[a-f]`는 정확히 **5글자** |
| `XX1abcde_hello<IP>world<TAB>...` (앞뒤 잡음) | 통과 | **앵커가 없어** 어디서든 매칭 |

"pass"를 그냥 넣은 것과 공백으로 넣은 것이 **둘 다 `Wrong`** 이고,
탭(`%09`)으로 넣었을 때만 통과한다는 점에서 `\t`가 탭이라는 해석이 확정된다.

## 5. 결과

정답 `val`을 보내자 `solve(11)`이 호출되고 `old-11 Pwned!` 알림과 함께 통과했다.

```
old-11 Pwned. You got 30point. Congratz!
```

문제 목록에서도 **`✔️ old-11`** 로 풀린 것을 확인했다.

> 이 문제도 **따로 제출할 플래그가 없다.** `val`이 서버가 만든 정규식에 매칭되는 순간
> `solve(11)`이 호출돼 바로 통과한다. "비밀 값을 알아내는" 문제가 아니라
> **패턴을 정확히 해석해 그에 맞는 입력을 만들어 보내는** 문제다.

## 6. 왜 이렇게 읽기 어려운가 — 그리고 일반화할 교훈

이 문제는 "공격"보다 **"문자열이 어떤 단계를 거쳐 최종적으로 무엇이 되는가"**
를 끝까지 따라가는 연습에 가깝다. 실무로 옮기면 두 가지 교훈이 남는다.

**(1) 정규식을 변수로 동적 조립하지 마라.**
`$_SERVER[REMOTE_ADDR]` 같은 외부에서 영향받는 값을 패턴 문자열에 그대로 끼워 넣으면,
그 값에 정규식 메타문자(`.`·`*`·`(`·`)` 등)가 섞일 때 패턴 자체가 바뀐다.
이번엔 IP라 점(`.`)뿐이었지만, 사용자가 통제하는 값을 패턴에 넣으면
**ReDoS(정규식 폭발)나 의도치 않은 매칭**으로 이어질 수 있다. 꼭 넣어야 한다면
`preg_quote()`로 메타문자를 이스케이프해야 한다.

```php
// 나쁨: 외부 값이 패턴 문법에 직접 섞인다
$pat = "/.*$_SERVER[REMOTE_ADDR].*/";
// 좋음: 리터럴로 취급
$pat = "/.*" . preg_quote($_SERVER['REMOTE_ADDR'], '/') . ".*/";
```

**(2) 문자열 리터럴의 이스케이프 규칙을 혼동하지 마라.**
`\t`는 **큰따옴표**에서는 탭, **작은따옴표**에서는 `\`+`t` 두 글자다.
"코드에 적힌 글자"와 "런타임의 실제 값"을 구분하지 못하면,
검증 로직이 **내 의도와 다른 것을 검사**하게 된다. 특히 정규식·SQL·셸 명령처럼
문자열이 또 다른 언어로 해석되는 곳에서 이 혼동은 버그이자 취약점의 씨앗이 된다.

**(3) 앵커 없는 매칭은 "포함"만 본다.**
`preg_match("/admin/", $x)`는 `x`가 `admin`인지가 아니라 `admin`을 **포함**하는지를 본다.
입력 전체를 검증하려면 `^`·`$`로 묶어야 한다(`"/^admin$/"`). 앵커 누락은
인증·필터 우회의 단골 원인이다.

## 7. 정리

- old-11은 **정규식을 정확히 해석하는** 문제다 — 패턴은 `/[1-3][a-f]{5}_.*<내IP>.*\tp\ta\ts\ts/`.
- 패턴이 **큰따옴표**라서 `$_SERVER[REMOTE_ADDR]`이 **보간**돼 **접속자 IP가 패턴에 박히고**, `\t`는 문자가 아니라 **탭**이 된다 — "pass"나 공백으로는 안 되고 **탭 4개**가 필요하다.
- 최종 입력 `1abcde_<내IP>\tp\ta\ts\ts`(탭=`%09`)를 `val`로 보내면 통과한다.
- 실무 교훈: **정규식을 외부 값으로 동적 조립하지 말고**(필요하면 `preg_quote`), **큰따옴표/작은따옴표의 이스케이프 차이**를 의식하며, **입력 전체 검증엔 앵커(`^`·`$`)** 를 쓴다.

> "소스에 적힌 글자"가 아니라 "런타임에 그 문자열이 실제로 무엇이 되는가"를 먼저 묻는다.
