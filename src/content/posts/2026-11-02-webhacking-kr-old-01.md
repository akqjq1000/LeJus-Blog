[webhacking.kr](https://webhacking.kr)의 **old-01** 문제를 풀었다.
필터 우회도 SQL 인젝션도 아니다. **권한 레벨을 쿠키 하나로 클라이언트가 정한다**는
접근 통제 실패에, **경계 비교 로직의 틈**이 겹친 문제다.
핵심은 두 가지다. 서버가 "내 레벨"이라고 믿는 값이 사실 **내가 보낸 쿠키**(`user_lv`)라는 점,
그리고 그 값을 검사하는 로직이 `is_numeric`(정수뿐 아니라 **실수도** 통과) + `>=4면 리셋` + `>3이면 통과`
라서 **`3 < x < 4`** 구간이 그대로 뚫린다는 점이다.

"쿠키를 바꿔 레벨을 올린다"에서 멈추지 않고, **각 분기(비교·리셋)가 실제로 어떤 값에서
어떻게 동작하는지**를 여러 값으로 직접 넣어가며 확인했다.
아래 내용은 전부 **실제로 서버에 요청을 넣어 응답을 확인한 것**이다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-01 (`/challenge/web-01/`) |
| 유형 | 접근 통제 실패 / PHP 타입 경계(type juggling) |
| 배점 | 20점 |
| 목표 | `user_lv`가 **레벨 4 이상으로 판정**되어 통과(`solve(1)`) |

페이지에 처음 들어가면 검은 화면에 **`level : 1`** 만 떠 있고, 하단에 `view-source` 링크가 있다.
서버는 접속하면 `user_lv` 쿠키가 없을 때 이를 `1`로 심어주고 페이지를 새로고침한다.

## 2. 정보 수집 — 소스 코드

하단 `view-source` 링크(`?view-source=1`)로 전체 로직이 공개된다. 핵심만 추리면 다음과 같다.

```php
<?php
  include "../../config.php";
  if($_GET['view-source'] == 1){ view_source(); }

  // user_lv 쿠키가 없으면 1로 심고 새로고침
  if(!$_COOKIE['user_lv']){
    SetCookie("user_lv","1",time()+86400*30,"/challenge/web-01/");
    echo("<meta http-equiv=refresh content=0>");
  }
?>
...
<?php
  if(!is_numeric($_COOKIE['user_lv'])) $_COOKIE['user_lv']=1; // (A) 숫자 아니면 1
  if($_COOKIE['user_lv']>=4)           $_COOKIE['user_lv']=1; // (B) 4 이상이면 1
  if($_COOKIE['user_lv']>3)            solve(1);              // (C) 3 초과면 통과
  echo "<br>level : {$_COOKIE['user_lv']}";
?>
```

읽어 보면 로직이 명확하다. 서버는 **접속자의 레벨을 어디에도 저장하지 않고**,
오로지 **쿠키 `user_lv` 값 하나**를 그대로 "내 레벨"로 쓴다.
그리고 그 값에 대해 세 줄의 검사를 순서대로 돌린다.

1. **(A)** 숫자가 아니면 `1`로 되돌린다.
2. **(B)** `4` 이상이면 `1`로 되돌린다.
3. **(C)** `3`을 **초과**하면 `solve(1)` — 통과.

## 3. 문제점 — 어디가 취약한가

### 3-1. 권한 레벨을 클라이언트가 보낸 쿠키로 정한다

이 문제의 본질은 **접근 통제 실패**다.
"내가 몇 레벨인가"는 서버가 세션·DB로 관리해야 할 사실인데,
여기서는 그 값이 **클라이언트가 자유롭게 바꿀 수 있는 쿠키**에 들어 있다.
쿠키는 브라우저가 들고 다니는 값이므로, 개발자도구·확장프로그램·프록시 어디서든
**원하는 값으로 바꿔 보낼 수 있다.** 서버가 "레벨"이라고 믿는 순간 이미 신뢰가 무너진다.

### 3-2. `is_numeric`은 정수만 통과시키지 않는다 — 실수도 숫자다

(B)·(C)의 비교가 **정수 레벨(1,2,3,4…)만 들어온다는 가정** 위에 서 있다는 게 틈이다.
정수만 가능하다면 `>=4`(리셋)와 `>3`(통과) 사이에는 **들어갈 값이 없다.**
`4`는 리셋되고, `3`은 `>3`이 아니라서 통과하지 못하기 때문이다.

그런데 (A)의 `is_numeric`은 **정수뿐 아니라 실수 문자열도 "숫자"로 인정**한다.
즉 `"3.1"` 같은 값이 (A)를 그대로 통과한다. 그러면 (B)·(C)의 수치 비교에서
`3.1`은 **`>=4`가 아니고(리셋 안 됨)**, 동시에 **`>3`은 참(통과)** 이 된다.
`3 < x < 4` 라는, 설계자가 "정수만 온다"고 가정하며 **비워 둔 구간**이 그대로 공격 지점이 된다.

> 핵심은 이것이다. 레벨은 `1,2,3,4`만 온다고 **가정**했지만, `is_numeric`은 그 가정을 지켜 주지 않는다.
> 경계(`>=4` 리셋 / `>3` 통과)를 정수 기준으로 잡아 둔 탓에 **그 사이의 실수 한 개면 뚫린다.**

## 4. 익스플로잇 — 페이로드 설계와 검증

필요한 조건은 세 가지를 동시에 만족하는 `user_lv` 값이다.

- (A) 통과: **숫자여야** 한다(`is_numeric` 참).
- (B) 회피: **`4` 미만**이어야 한다(리셋 안 됨).
- (C) 성립: **`3` 초과**여야 한다(통과).

세 조건의 교집합은 **`3 < user_lv < 4`**. 가장 단순한 값은 **`3.1`** 이다.

### 4-1. 분기 동작을 값별로 직접 확인

페이로드를 넣기 전에, 각 분기가 실제로 어떻게 도는지 **여러 값을 직접 넣어**
서버가 echo 하는 `level : …` 과 통과 여부를 확인했다.
쿠키는 문제 경로(`/challenge/web-01/`)에 맞춰 심고 페이지를 요청했다.

| 넣은 `user_lv` | 서버가 보여준 level | 통과 | 이유 |
| --- | --- | --- | --- |
| `1` (기본값) | `1` | ✗ | `>3`이 아님 |
| `3` | `3` | ✗ | `3>3`은 **거짓** |
| `3.0` | `3.0` | ✗ | `3.0>3`도 거짓 |
| **`3.1`** | **`3.1`** | **✓** | `>=4` 아님 + `>3` 참 |
| `3.9` | `3.9` | ✓ | 같은 구간 |
| `4` | `1` | ✗ | (B) `>=4` → 리셋 |
| `5` | `1` | ✗ | (B) 리셋 |
| `admin` | `1` | ✗ | (A) 숫자 아님 → 리셋 |
| `0x5` | `1` | ✗ | PHP 7+에서 `is_numeric("0x5")`는 **거짓** → 리셋 |
| `1e1` | `1` | ✗ | 숫자(=10)지만 `>=4` → (B) 리셋 |

읽어낼 점이 몇 가지 있다.

- **정수로는 뚫을 수 없다.** `3`은 `>3`을 못 넘고, `4` 이상은 (B)가 리셋한다 — 그래서 **실수**가 필요하다.
- `0x5`(16진 문자열)는 PHP 7 이후 **`is_numeric`에서 더 이상 숫자가 아니다.** 실제로 level 1로 리셋됐다 — 추측이 아니라 넣어서 확인했다.
- `1e1`(지수 표기)은 `is_numeric`엔 통과하지만 값이 `10`이라 (B)에서 리셋된다.

### 4-2. 최종 페이로드 주입

레벨 통과 구간에 들어가는 값 `3.1`을 쿠키로 심고 문제 페이지를 요청했다.
쿠키 경로는 소스의 `SetCookie(..., "/challenge/web-01/")`에 맞춘다.

```js
// 브라우저 콘솔(같은 출처)에서 쿠키를 심고 문제 페이지를 요청
document.cookie = "user_lv=3.1; path=/challenge/web-01/";
await fetch('/challenge/web-01/', { credentials: 'include' }).then(r => r.text());
```

```console
GET /challenge/web-01/   (Cookie: user_lv=3.1)
→ ... old-01 Pwned. You got 20point. Congratz!  level : 3.1
```

## 5. 결과

`user_lv=3.1`을 넣은 요청에서 서버가 바로 통과 처리했다.

```
old-01 Pwned. You got 20point. Congratz!
level : 3.1
```

문제 목록(`chall.php`)에서도 **`✔️ old-01`** 로 풀린 것을 확인했다.

> 이 문제도 **따로 제출할 플래그가 없다.** 조건(`user_lv>3` & `<4` & 숫자)을 만족하는
> 쿠키를 넣는 순간 서버가 `solve(1)`을 호출한다.

## 6. 왜 취약한가 — 그리고 올바른 방어

**(1) 권한·신원 값을 클라이언트에 맡기지 마라.**
레벨·역할·소유자 같은 값은 **서버 세션이나 DB**에서 관리해야 한다.
쿠키·파라미터로 받은 값을 그대로 권한 판단에 쓰면, 그 값은 더 이상 사실이 아니라
**공격자가 고르는 입력**이다.

```php
// 나쁨: 권한 레벨을 클라이언트 쿠키로 결정
$lv = $_COOKIE['user_lv'];

// 좋음: 인증된 세션에서 서버가 아는 값만 사용
session_start();
$lv = $_SESSION['user_lv'];   // 로그인 시 서버가 설정, 클라이언트가 못 바꿈
```

**(2) 경계 비교는 입력 타입까지 고정해서 설계하라.**
`>=4`로 막고 `>3`으로 통과시키는 구조는 "정수만 온다"는 가정에서만 안전하다.
`is_numeric`은 **실수·지수 표기까지 숫자로 인정**하므로 그 가정이 깨진다.
값을 쓰기 전에 **정수로 강제(캐스팅)** 하거나, **허용 목록으로 범위를 못 박아야** 한다.

```php
// 실수/지수까지 들어올 수 있으니, 정수로 고정하고 범위를 명시적으로 검사
$lv = (int)$_COOKIE['user_lv'];        // 3.1 → 3 으로 잘림
if ($lv < 1 || $lv > 5) { $lv = 1; }   // 허용 범위 밖은 거부
```

**(3) "숫자인가"와 "내가 원하는 숫자인가"는 다르다.**
`is_numeric` 통과 여부만 믿으면 `3.1`·`1e1`·음수·아주 큰 수 등 예상 밖 값이 들어온다.
**형식 검증(숫자?)과 값 검증(허용 범위?)을 분리**해서 둘 다 확인해야 한다.

## 7. 정리

- old-01은 **권한 레벨(`user_lv`)을 클라이언트 쿠키로 정하는** 접근 통제 실패 문제다.
- 로직은 `is_numeric`(A) → `>=4면 리셋`(B) → `>3이면 통과`(C) 순서인데, **정수만 온다는 가정** 때문에 `3 < x < 4` 구간이 비어 있다.
- `is_numeric`은 **실수도 숫자로 인정**하므로 **`user_lv=3.1`** 이면 (B)를 피하고 (C)를 만족해 통과한다 — `3`·`3.0`은 `>3`이 아니라 안 되고, `4`·`5`는 (B)가 리셋한다.
- `0x5`는 PHP 7+에서 비숫자로 리셋되고, `1e1`(=10)은 숫자지만 (B)로 리셋됨을 **직접 넣어 확인**했다.
- 실무 교훈: **권한 값은 서버에서 관리**하고, **경계 비교는 입력 타입을 고정**하며, **"숫자인가"와 "허용 범위의 값인가"를 둘 다 검증**한다.

> "이 값이 숫자인가"가 아니라 "이 값을 **클라이언트가 정하게 두어도 되는가**, 그리고 내가 가정한 타입·범위를 **정말 지키는가**"를 먼저 묻는다.
